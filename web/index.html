A / EXPERIMENT ENGINE

Compare policies fairly.

marg.sim.world builds seeded gateways, context drift, and outage windows. Each strategy gets the same precomputed world and per-transaction random draws, so route choices are the variable under test. Routers receive context, time, and observed success only; true success probabilities stay inside the simulator.

Key path: bench.run_routing → marg.routing → results/routing.json and plots.

B / FRAUD PIPELINE

Score in time order.

marg.fraud.data sorts by transaction time and splits train, validation, and test periods. The model uses the earlier period; thresholds are chosen on validation data and evaluated on the later test period. PR-AUC and recall at 1% FPR describe rare fraud more usefully than accuracy.

Key path: marg.fraud.train → model and thresholds → results/fraud_metrics.json.

C / ONLINE SERVICE

Keep the hot path small.

marg.fraud.serve.create_app loads the model once. POST /score validates 30 floats, predicts a score, then maps it through saved thresholds. SHAP is initialized lazily on POST /explain, a separate call used for investigation instead of every scoring request.

Key path: FastAPI serves this page, /health, /api/results, /score, and /explain.

D / OPERATIONS AND AGENT

Observe, then investigate.

The outage detector sees gateway outcomes and raises alerts; the simulator’s outage schedule is used only afterward to score detections, misses, false alarms, and delay. The optional investigator validates a structured LLM report and rejects risk factors outside the supplied SHAP list. It cannot alter a model decision.

Safety boundary: gateway dispatch is disabled by default; there is no live payment adapter.

WHY THE FRONTEND MATTERS

It makes the backend inspectable: saved results load from GET /api/results, the playground calls the real local service, and each number links back to generated JSON. A browser smoke check verifies those routes. Tests and full benchmark generation remain explicit terminal jobs so a webpage cannot trigger arbitrary shell execution.

04 / THE INTERVIEW STORY

Show the thinking.
Own the limits.

Juspay publicly describes rule-based routing and dynamic gateway ordering; its blog discusses recent performance, sliding windows, exploration, and downtime detection. Marg is relevant as a small learning project, not a replica of their production system.

“

I built a seeded payment-routing simulator and compared fixed, heuristic, and adaptive policies under drift and outages. I used common random numbers so strategies faced the same world and per-transaction draws. Separately, I trained a fraud model with a chronological split and kept SHAP outside the scoring endpoint. The routing is synthetic, the fraud data is historical and anonymized, and my local client p99 still misses the target. The exact measurements are in the generated results table.

A SHORT VERSION — THEN OPEN THE CODE
Why Thompson sampling over epsilon-greedy?

Posterior sampling explores in proportion to uncertainty and observed performance. Here the non-stationary window forgets old outcomes. The benchmark compares both; Thompson is better in this configured simulator, which is not a production guarantee.

What does the window size trade off?

A short window reacts quickly but has noisier estimates. A long window smooths noise but adapts slowly. The saved sweep in results/window_sweep.json is the evidence; the winner depends on this world’s drift and outage cadence.

How do you separate an outage from random failures?

Use only observed outcomes and compare recent performance to a baseline, then report detection rate, false alarms, and delay together. The current detector misses outages, and sparse probe evidence is one measured reason. The chart above shows the tradeoff.

Why keep SHAP out of /score?

Tree SHAP adds work and is only needed for selected cases. The API computes the model decision first; /explain is a separate request. This keeps the hot path simpler and makes its cost measurable.

What fails first at 350M transactions a day?

This project does not prove a scale limit. I would first remove local-client measurement ambiguity, profile serialization and scheduling, then test a distributed serving setup with realistic concurrency, feature access, tail budgets, and failure behavior. The local client p99 misses the target; its measured residual is mostly client/loopback/response work, not model inference.

How does this compare with Juspay’s published routing work?

Their paper describes delayed feedback, exploration, sliding-window gateway scores, downtime detection, cascading retries, and A/B configuration. Marg models a simpler per-context bandit with synthetic outcomes and common random numbers. A useful next experiment is to implement an observed-outcome feedback controller baseline and compare both under delayed feedback.

WHY THE FIT IS PLAUSIBLE

Juspay’s backend role publicly lists intelligent traffic routing, self-healing systems, automatic anomaly detection, and AI-powered payment operations. That is direct topic overlap. Interviews also test fundamentals; this project complements DSA, concurrency, and system design practice rather than replacing it. See current backend role ↗

05 / LIMITATIONS

Honesty is
part of the build.

01

Synthetic gateway world. Success rates, traffic, and outages are simulated; results do not predict real payment lift.

02

Historical anonymized fraud data. V1–V28 have no human-readable semantics; later-period performance can shift.

03

Latency target missed. Local client p99 is reported separately from ASGI app and model inference; no remote load generator has been used.

04

Proxy costs only. Amount is not confirmed as currency or actual fraud loss. Review assumptions are hypothetical.

05

No production integration. No live payment rails, durable idempotency store, authentication, or production operator controls.
